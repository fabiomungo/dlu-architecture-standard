# ADR-0023 — Course Creation v2.0/2.1/2.2 alignment: multi-CLO contribution via the existing `mlo_clo_alignments` table, CIV-01 as the single validator, Factory as a real producer

Status: Accepted (2026-08-13, implemented — CCV2-01 through CCV2-06/CCV2-10, see TRACEABILITY.md)
Related: ADR-0017 (Course Exchange Format v2.0), ADR-0019 (EKG platform subsystem), ADR-0022 (PostgreSQL as interim academic source of truth)
Source: `COURSE_CREATION_V2_ALIGNMENT_PLAN.md` (`dlu_builder_tk`, 12 August 2026), CCV2-01…CCV2-10 build/investigation across ten sprints

## Context

ADR-0017 already accepted the Course Exchange Format v2.0 file shape. What remained open was how the three systems that actually produce and consume courses — Course Factory, Course Composer, and the Course Exchange service — would be brought up to that shape, and specifically how an MLO's contribution to more than one CLO would be modeled: the original alignment plan proposed a **new** association table for this.

Live investigation (CCV2-01) found this proposal was already stale before implementation started: `MLOtoCLO` (`backend/database/models_learning_outcomes.py`, table `mlo_clo_alignments`) already existed as a real, unique-constrained-on-the-pair, many-to-many table — built for an earlier, unrelated sprint — but had no producer/consumer wired to it. `MLO.clo_id` (a single legacy FK) was the only thing `academic_outcome_projection.py`'s `CONTRIBUTES_TO` edge read from, meaning an MLO's real multi-CLO contribution was invisible to the graph even though the schema to express it already existed.

A second premise checked across every subsequent sprint: whether the plan's own sequencing and file-pointer assumptions held up against the actual codebase. They frequently didn't (see Decision, below) — this ADR exists partly to record that the shipped implementation diverges from the original plan document in several specific, load-bearing ways, and the plan document itself (`COURSE_CREATION_V2_ALIGNMENT_PLAN.md`) was never revised to match as each sprint completed.

## Options considered

1. **New CLO-contribution association table**, as the original plan proposed. Rejected: `mlo_clo_alignments` already exists, is already correctly shaped (unique on the pair, `alignment_strength` column), and a second table expressing the same relationship would only create a drift risk between two sources of truth for one fact.
2. **Keep `MLO.clo_id` as the only contribution signal**, treat `mlo_clo_alignments` as unused legacy scaffolding. Rejected: this is the status quo that made multi-CLO contribution invisible to the graph in the first place, and the table is real, live schema, not dead code — leaving it unread was the bug, not a reason to abandon it.
3. **Read `MLOtoCLO` for `CONTRIBUTES_TO`, keep `MLO.clo_id` as the single legacy fallback FK for pre-migration rows and as the row-level NOT NULL owner column** (Chosen). Additive, no new table, no destructive change to existing data; `MLO.clo_id` remains genuinely required at the DB level (confirmed unchanged since its origin migration, `20260510_1000_aci_00_01_academic_intelligence_foundation.py`) and is treated as "the first/primary CLO," while `MLOtoCLO` is the complete picture the graph projection actually reads.

## Decision

- **Multi-CLO contribution is `MLOtoCLO` (`mlo_clo_alignments`), not a new table.** `academic_outcome_projection.py::_structural_edges` emits one `CONTRIBUTES_TO` edge per `MLOtoCLO` row for an MLO, falling back to `mlo.clo_id` only when no alignment rows exist yet (pre-migration data). `backend/scripts/ccv2_01_backfill_mlo_clo_alignments.py` backfills exactly one alignment row (from `clo_id`) for any MLO with zero — real, idempotent, dry-run-first, already run and tested.
- **`CLO`/`MLO` carry real EKG outcome attributes** (`target_mastery`, `status`, `version`, `uri` — migration `20261008_0900_ccv2_01_outcome_ekg_attrs.py`), consumed directly by the v2.x exchange schema's own required `outcome` shape (`docs/dlu_course_exchange_v2.{0,1,2}.schema.json`). `backend/scripts/ccv2_backfill_outcome_attrs.py` (CCV2-07) closes NULLs on existing rows using the one convention established and shipped in CCV2-06 (`target_mastery` default `0.80`, `status` default `"draft"`, `version` default `"1.0"`) — not a newly-invented default, and discloses (rather than silently fixes) a related, ongoing gap: `POST /{course_id}/clos`'s `CLOCreate`/`CLOUpdate` schemas still have no fields for these 4 columns, so new CLOs created through that live route continue to need this backfill re-run until that schema surface is separately extended — a deliberate, out-of-scope-for-this-ADR product decision, not an oversight.
- **CIV-01 (`backend/services/course_invariants/validator.py::validate_course_exchange`) is the single validator** for all of v1.0-1.3 (unchanged), v2.0, v2.1 (`ekgBaseline`/`conceptRefs`/`externalPrerequisites`), and v2.2 (`catalog`/`ekgSnapshotOut`) — JSON-Schema plus cross-object invariants, pure and DB-session-free, fed a real `CourseInvariantPolicyParams` row (31 codes) resolved via `get_active_course_invariant_policy`. No parallel Pydantic model tree was built for the v2.x shapes specifically to avoid a second, driftable copy of the same three JSON Schemas already being the source of truth.
- **The v2.x exporter/importer (`backend/services/course_exchange_v2_service.py`, CCV2-05) is genuinely additive** alongside the fully-live v1.0-1.3 `course_exchange_service.py`, not a rewrite. Concepts are sourced from `CanonicalConcept`/`ConceptOccurrence`/`ConceptPrerequisite` (ADR-0024), never the legacy per-course `KnowledgeGraphNode`. Catalogue binding (v2.2) resolves against `CourseCatalogItem` at generation time (Course Factory, CCV2-06) and `CatalogEdition` at export/citation time (CCV2-05) — two different tables for two different lifecycle stages of the same underlying institutional catalogue, not competing sources (`CatalogEdition.snapshot` is itself built from `CourseCatalogItem` rows, confirmed in `catalog_edition_service.py::_build_snapshot`).
- **Course Factory is now a real producer**, not just a schema target: `_persist_ontology` sets the 4 outcome attributes on every AI-generated CLO/MLO; `_register_concepts_and_assessments` (new in CCV2-06) tags lessons via the real NLP extractor, resolves labels against the canonical registry (ADR-0024) before ever declaring a new concept, and creates real `AssessmentItem`/`ItemOutcomeAlignment` rows per generated quiz question — closing three previously-built, previously-unused ("correct and ready, no live producer") services' first real call site in one sprint.
- **The plan document's own file-pointers were wrong in specific, confirmed ways** and were never corrected as work landed: it cites `models_course_catalog.py` for the institutional catalogue (an unrelated model from an earlier, different sprint — the real backing is `CatalogEdition`, sourced from `CourseCatalogItem`), assumes CCV2-05 depends on CCV2-10 (it doesn't), assumes Programme/Institution EKG course membership comes from `CatalogEdition` (CCV2-10 uses live `ProgramCourse` instead, to satisfy its own "incremental growth on publish" requirement), and cites the wrong next-free ADR numbers (0022/0023, both already taken by unrelated ADRs — the real numbers are 0023/0024, this ADR and ADR-0024). None of these were silently worked around; each was investigated, resolved, and disclosed in its own sprint's commit message before building on the corrected understanding.

## Consequences

**Positive:** no new association table to keep in sync with `mlo_clo_alignments`; one validator for every supported format version, past and present; Course Factory output is now real EKG-graph-ready data instead of a schema shape with nothing behind it; the catalogue-binding split (`CourseCatalogItem` vs `CatalogEdition`) lets generation-time validation stay live while export-time citation stays frozen and auditable.
**Costs/risks:** `CLOCreate`/`CLOUpdate`'s missing outcome-attribute fields remain a live gap — every CLO created via that route still needs the backfill re-run until that schema is separately extended; this ADR does not resolve it, only names it plainly. The committed `COURSE_CREATION_V2_ALIGNMENT_PLAN.md` itself still contains the stale citations described above as of this ADR's acceptance — it was treated as a historical specification, not kept as a living document, and a reader consulting it directly (rather than this ADR/TRACEABILITY.md) will hit those errors.
**Enforcement:** `validate_course_exchange` is the only code path that accepts a v2.x payload as valid; `academic_outcome_projection.py` is the only code path producing `CONTRIBUTES_TO` edges, and it reads `MLOtoCLO` first.
