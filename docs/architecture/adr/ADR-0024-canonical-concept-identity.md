# ADR-0024 — `CanonicalConcept` is the identity authority for the EKG `Concept` node type, replacing course-scoped `KnowledgeGraphNode` going forward

Status: Accepted (2026-08-13, implemented — CCV2-08/CCV2-09/CCV2-10, see TRACEABILITY.md)
Related: ADR-0019 (EKG platform subsystem), ADR-0021 (EKG usage & RKG governance plane), ADR-0023 (Course Creation v2.0/2.1/2.2 alignment)
Source: `COURSE_CREATION_V2_ALIGNMENT_PLAN.md` §2.7 (`dlu_builder_tk`), CCV2-08/09/10 build/investigation

## Context

The EKG Ontology (1.0) already registers `Concept` (Knowledge layer) and `PREREQUISITE_OF` ("directed acyclic prerequisite relation") as formal node/edge types — no new ontology registration was needed to introduce the *type*. What didn't exist was a real, cross-course identity for a concept: `KnowledgeGraphNode` (`node_type='concept'`) is scoped to one course's own graph, so the same concept taught in two courses (e.g. "Gradient Descent" in both an ML and a Deep Learning course) had no way to be recognized as the same thing — every course independently declared its own copy, with no deduplication and no way to express a prerequisite that crosses a course boundary.

A real, empirically-derived fixture (`docs/ekg-examples/`, a validated 2-course EKG instance) quantified the cost of this: 27 concepts declared naively across two courses, only 22 of which are actually distinct — an 18.5% duplication rate — with 5 concepts genuinely shared and 4 genuine cross-course prerequisite dependencies invisible to any single course's own graph.

## Options considered

1. **Extend `KnowledgeGraphNode` itself with a cross-course identity column.** Rejected: `KnowledgeGraphNode` is scoped by `graph_id` (one graph per course) at the schema level; retrofitting cross-course identity onto it would mean either a destructive schema change to already-live data, or a parallel identity scheme bolted onto a table whose whole shape assumes course-locality.
2. **A new, platform-scoped `CanonicalConcept` table, additive alongside the existing `KnowledgeGraph`/`KnowledgeGraphNode` tables, with no destructive change to either** (Chosen). `CanonicalConcept` (GUID PK, `tenant_id` nullable-means-global, unique `uri`) becomes the identity; `ConceptOccurrence` records which course/lesson teaches it; `ConceptAlias` records alternate labels resolving to one concept; `ConceptPrerequisite` records the cross-course-capable `PREREQUISITE_OF` relationship, cycle-checked against the ontology's own "directed acyclic" semantics via the same shared DFS helper CIV-01 already implemented (`backend.services.graph.cycle_check`, extracted once a second caller needed it, not re-forked).

## Decision

- **`CanonicalConcept` is the new identity authority for the `Concept` node type.** `KnowledgeGraphNode`/`KnowledgeGraph` are untouched and remain live — nothing reads them as dead — but the forward path for concept identity is `CanonicalConcept`, not a new `KnowledgeGraphNode` row per course.
- **Resolution, not blind creation, is the rule everywhere a concept is proposed.** `concept_merge_stewardship_service.py::resolve_concept_reference` (CCV2-09) returns a tri-state confidence: `registry` (exact pref_label/alias match), `steward` (an already-approved prior merge decision), `ai_suggested` (a pg_trgm-similarity candidate below full confidence), or no match at all. Every real caller built this track — Course Factory's `_register_concepts_and_assessments` (CCV2-06), the v2.1 exchange format's `conceptRefs[]` resolution on import (CCV2-05), and the CCV2-07 legacy backfill — treats `registry`/`steward` as safe to auto-apply, treats a genuine no-match as safe to create fresh, and treats `ai_suggested` as **never** auto-applied: a lower-confidence similarity candidate is real, meaningful signal that a human steward should see, not something a bulk process silently accepts or silently discards. This is the same rule in three independent call sites, not restated three different ways.
- **Merge governance required one real, new ontology registration** — the sole ontology-governance step this whole ten-sprint track needed. `MappingAssertion` (Governance layer) already existed but is specifically internal-skill↔external-framework, not concept↔concept; CCV2-09 registered a new node type `ConceptMergeAssertion` plus `PROPOSES_MERGE_OF`/`PROPOSES_MERGE_INTO` edge types via the real draft→review→publish `EkgOntologyVersion` lifecycle (version `1.2.0`, cloning the prior version's full 48 node types/61 edge types/5 SHACL shapes forward, per the established "complete self-contained supersets" convention), not a bare table with no registry entry.
- **A merge is reversible by construction.** `ConceptMergeAssertion.merge_manifest` records exactly which `ConceptOccurrence`/`ConceptPrerequisite` rows an approved merge repointed, so `split_merge` reverses precisely those rows — not a heuristic guess at what to undo.
- **Cross-course prerequisite has one strict, agreed definition**, used consistently everywhere it matters: `canonical_concept_service.is_cross_course_prerequisite` — true iff no single course teaches both endpoints (disjoint taught-in-course sets). This was deliberately chosen over a looser notion found in the Course Builder's own reference JS (`docs/ekg-examples/e2e_baseline_test.mjs`), which counts one additional pair (`gradient-descent → backpropagation`) that is **not** disjoint under the strict definition (gradient-descent is taught in both source courses) — the already-tested backend definition governs; the Builder's reference implementation is not treated as an equally-valid second authority.
- **The Programme/Institution EKG (CCV2-10) needed no new merge/dedup logic of its own** — `concept_to_snapshot_entry` (the per-concept payload builder, CCV2-08) already accepts an arbitrary `occurrences` iterable and folds every course's contribution into one `taughtIn[]`; calling it once per concept across every course in a programme's scope, instead of once per course, **is** the de-duplication. `ProgramEkgSnapshot` (CCV2-10) adds only the one genuinely new piece of state: a monotonically-versioned, append-only record of each published union, computed fresh from live `ConceptOccurrence` data on every publish (never a separate rebuild step) — matching this track's own "incremental growth on publish" requirement, and deliberately resolving programme/institution course membership from live `ProgramCourse` rows rather than the separately-published, citation-grade `CatalogEdition` snapshot, so growth is never blocked on a separate, infrequent institutional publishing cadence.
- **Legacy `KnowledgeGraphNode` concept data is migrated forward, not abandoned.** `backend/scripts/ccv2_backfill_canonical_concepts.py` (CCV2-07) resolves every concept-type node with no matching `ConceptOccurrence` yet through the same `resolve_concept_reference` tri-state rule, real and confirmed sources of such nodes being `seed_ekg_demo.py`'s direct node creation and the still-live generic `POST /{course_id}/nodes` route — both of which bypass canonical resolution entirely and would otherwise keep accumulating unresolved legacy data indefinitely.

## Consequences

**Positive:** one identity per real-world concept regardless of how many courses teach it, confirmed against a real fixture (22 canonical concepts, not the naive 27); a merge decision is auditable and reversible rather than a silent overwrite; the Programme/Institution union required zero new deduplication code because the identity model was designed for exactly this from CCV2-08 onward.
**Costs/risks:** two parallel concept representations now coexist in the codebase (`KnowledgeGraphNode` for anything not yet migrated, `CanonicalConcept` as the forward identity) until the CCV2-07 backfill (and any future direct-node-creation call sites it doesn't cover, like `POST /{course_id}/nodes`) fully closes the gap; the `ai_suggested` tier's "never auto-apply" rule means a real steward console/queue must exist for those cases to ever get resolved, not just deferred forever.
**Enforcement:** `canonical_concept_service.py`/`concept_merge_stewardship_service.py` are the only code paths permitted to create or merge a `CanonicalConcept`; every other service (Course Factory, the v2.x exchange importer, the CCV2-07 backfill) calls into one of these two rather than writing to `canonical_concepts`/`concept_occurrences` directly.
