# ADR-0025 — Course invariants are server-authoritative at every gate and projection point, not just client-side

Status: Accepted (2026-08-14, implemented — CIV-01…05, see TRACEABILITY.md)
Related: ADR-0017 (Course Exchange Format v2), ADR-0019 (EKG platform subsystem), ADR-0023 (Course Creation v2.0/2.1/2.2 alignment), ADR-0024 (Canonical Concept Identity)
Source: `docs/ROOCODE_COURSE_INVARIANTS_PROMPTS.md` (`dlu_builder_tk`), CIV-01…06 build/investigation

## Context

Before this track, the EKG course invariants (structural shape, cross-object referential integrity, assessment coverage, acyclicity, catalogue binding) were enforced in exactly one place with real teeth: the HTML Course Builder's own client-side `validate()`, backed by a JSON Schema for the structural subset. Nothing on the server re-checked any of it. A course produced by any other client — or by the platform's own Course Factory/Composer, or a hand-edited exchange file posted directly to the API — could pass every governance gate and be projected straight into the EKG with zero invariant enforcement, regardless of what the Builder would have refused to export.

CIV-01/CIV-02 (an earlier phase of this same track) already built the fix for "what should the rules be and where do they live": a single, versioned, server-side rule pack (`CourseInvariantPolicyParams`) and a validator (`validate_course_exchange`, `backend/services/course_invariants/validator.py`) that ports the Builder's own logic faithfully, kept in lock-step by a cross-client parity test. What remained open at the start of this ADR's own sprints (CIV-03…05) was purely **enforcement**: the validator existed and was correct, but nothing actually *called* it at the two points that matter — a governance gate transition, and EKG projection — and no CI check existed to stop the three surfaces (schema, validator, Builder) from drifting apart again.

**A real, load-bearing finding surfaced immediately on investigation, before any gate could be safely switched on**: every course export in the system was, at the time, unconditionally failing the validator — undetected only because every existing test exercising the export/publish path explicitly passed `validate=False`. Switching CIV-03/04's gates on against that reality would have blocked every course in the system on day one. Six real, independent bugs (a missing top-level `uri`/`version`/`status` on the exported course object, a `teaches` payload that referenced the wrong concept identifier, a multi-MLO alignment gap in Course Factory's own producer, a dead import of a Celery task that has never existed under that name, and two smaller schema-completeness gaps) had to be found and fixed first — see the `fix(ekg): close 6 real gaps…` commit — before the gates in this ADR could be turned on without breaking every course in the system.

## Options considered

1. **Re-validate at every possible entry point** (every route that can mutate a course). Rejected as unbounded scope creep: most such routes don't produce a *release-shaped* artifact (a complete, exportable course) — they mutate one field of one CLO. Validating there would mean re-deriving "is this a complete course" logic at dozens of call sites, or accepting false-positive blocks on legitimately in-progress drafts.
2. **Validate only at the JSON Schema layer, client + CI.** Rejected: the schema is deliberately the *structural* subset only (per CIV-01's own architecture principle) — it cannot express a prerequisite cycle, a dangling reference, or "every published outcome is assessed." A schema-only gate would let every cross-object invariant this track exists for slip straight through.
3. **Validate at exactly the two points where an invalid course can do real, irreversible damage — a governance gate transition, and EKG projection — plus a CI merge gate to keep the three enforcement surfaces (schema/validator/Builder) from drifting apart** (Chosen). This matches the validator's own designed call shape (`validate_course_exchange(payload, rules, *, live_coverage=None, catalog=None)` — a pure function over a release-shaped payload, not a per-field checker) and requires no new abstraction: `civ_gate_check` (CIV-03) and the projection guard (CIV-04) both just call `export_course_v2(..., validate=True)`, the same code path that already assembles a release-shaped payload for any other consumer.

## Decision

- **Gate guard (CIV-03).** `course_workflow.civ_gate_check(db, course, *, gate=None, waiver_reason=None)` runs the real validator (via `export_course_v2(..., validate=True)`) before Gate 2 (`submit_review`, unconditional), Gate 3 (`gate3_final_approval`, only on an `approve` decision), and `publish` (unconditional). **Gate 1 is deliberately not gated** — at that point in the workflow no lesson/assessment content exists yet, so the validator would trivially fail on structure that hasn't been authored, not on a real defect; Gate 1's own pre-existing `blueprint_readiness` check remains its guard. A blocking result emits `course.validation.failed` (always) and `course.gate.blocked` (unless waived) through `event_taxonomy.py`'s closed taxonomy, then raises — no gate transition can complete with open blocking invariants.
- **Waiver plumbing is Phase-1 scope only, by design.** A caller may pass a `waiver_reason`; if present, the block is still recorded via `course.validation.failed` (so it is audited) but does not raise. **No approval workflow exists for a waiver** — it is a bare reason string, accepted at face value. Building steward/approval governance for waivers is explicitly deferred to Phase 2, matching CIV-03's own spec; this ADR records that deferral rather than silently open-ending it.
- **Projection guard (CIV-04).** `course_factory_worker._sync_course_to_kg_async` runs the same `export_course_v2(..., validate=True)` check before dispatching `kg_worker.build_course_graph`. A blocking result emits `course.projection.rejected` and the Celery task is never dispatched — the EKG cannot ingest a release that fails a blocking invariant. Found and fixed a real, independent, pre-existing bug while wiring this: the function being guarded had been importing a Celery task, `kg_worker.sync_course_to_kg`, that has never existed under that name anywhere in this codebase — every call silently hit `ImportError` and logged a debug line, meaning KG sync after Course Factory generation had never actually fired, at any point in this whole multi-sprint track, until this fix. The projection guard and the dead-import fix landed together because the guard could not otherwise be verified against a real dispatch.
- **CI merge gate (CIV-05).** `scripts/ci/validate_course_exchange.py` (wired into a new `.github/workflows/course-invariants.yml`, mirroring `kg-gates.yml`'s checkout/run shape) asserts the packaged schema pair (`backend/schemas/course_exchange_v2.2.schema.json`, `backend/schemas/course_catalog_v1.schema.json`) stays byte-identical to the `docs/` canonical copies, then runs the real pytest suite that owns the fixture-corpus/coverage-guard/Builder-parity checks — rather than re-deriving any of that logic a second time in the CI script itself. A PR that lets a schema copy drift, breaks a fixture's expected blocking codes, or adds a new blocking rule code with no fixture fails CI.
- **The rule set stays a versioned rule pack, not a hardcoded gate.** Nothing in CIV-03/04/05 hardcodes a rule code or level — every gate call goes through the same `CourseInvariantPolicyParams`-backed validator CIV-01 already built, so a future rule-pack version change (a new blocking code, a threshold change) takes effect at every enforcement point simultaneously, with no separate code path to update.

## Consequences

**Positive:** an invalid course cannot pass a governance gate or reach the EKG, regardless of which client produced it — closing the exact gap this ADR exists to close. Every block is audited (a `DomainEvent` row) and observable, not a silent rejection. The six real bugs this track's own investigation surfaced (see Context) are now fixed as a side effect of being forced to prove the gates work against real data, not left latent for a future incident to find.
**Costs/risks:** waiver governance remains genuinely Phase-1 — a reason string with no approval workflow — so a course can be pushed through a blocking failure by anyone with route access to the gate, with only an audit trail after the fact, not a preventive control. This is a known, accepted gap pending Phase-2 steward governance, not an oversight.
**Enforcement:** `civ_gate_check` and the projection guard are the only two places a course-workflow transition or a KG projection dispatch is permitted to skip straight past the validator (i.e., nowhere) — every other call site that reaches a gate or projection now passes through one of these two functions.
